# Code audit — 2026-09-22

> Scope: `src/beherouter/` (5 757 lines, 39 modules), `tests/` (622 tests),
> `Containerfile`, `charts/beherouter/`, `.github/workflows/`. Looking for
> duplicate, inefficient and outdated code, and for the gates that would have
> caught each finding before a human had to.
>
> **Headline: the code is in unusually good shape.** A structural
> duplicate-function scan over every function in `src/` returns two hits. A
> reachability scan over 188 public definitions returns zero genuine dead ones.
> A broad ruff ruleset (`I,UP,B,SIM,C4,PIE,RUF,ASYNC,LOG,PERF,W,E501,N`) finds
> 25 issues across 8 000+ lines of source and tests.
>
> What the audit *did* find clusters almost entirely in the **build and release
> plumbing** rather than in the gateway logic — the parts no test covers and no
> linter reads. That is also where the CI gates should go.

Severity is about consequence, not effort:

- **S1** — wrong output reaches a consumer today.
- **S2** — latent: correct now, breaks silently on a plausible future edit.
- **S3** — hygiene; no behavioural consequence.

## 1. Outdated

### 1.1 — S1 — The CLI reports version `0.1.0`; the package is `0.2.2`

`src/beherouter/cli/app.py:25`

```python
app = BeheaxiApp(
    name="beherouter",
    version="0.1.0",          # pyproject.toml says 0.2.2
```

Verified live:

```
$ uv run beherouter describe --json
{"tool": "beherouter", "version": "0.1.0", ...}
```

This is the one finding that is **wrong on the wire right now**. `describe
--json` is the beheaxi manifest — the conformance surface this repo dogfoods
and that `beheaxi conformance "beherouter"` reads — and it has been three
releases stale.

`release.yml` already gates `git tag == pyproject.version == chart appVersion`.
It never learned about the fourth place a version is written, so the gate that
exists to prevent exactly this class of drift steps around it.

**Fix:** read the version from package metadata rather than re-typing it:

```python
from importlib.metadata import version
app = BeheaxiApp(name="beherouter", version=version("beherouter"), ...)
```

That removes the register instead of adding a fourth thing to keep in sync.

### 1.2 — S3 — `Containerfile` cites `[tool.uv.sources]`, which no longer exists

`Containerfile:16-20`

```dockerfile
# `--no-sources` ignores the [tool.uv.sources] local-path override for beheaxi
# (there is no ../beheaxi in the build context) ...
RUN uv sync --no-sources --no-dev
```

`pyproject.toml` has no `[tool.uv.sources]` table — `ci.yml`'s own comment
records that it was deliberately dropped ("the reason `[tool.uv.sources]` was
dropped — so CI has to fail if it comes back"). The flag is now a no-op and the
comment sends the next reader looking for a table that is not there.

Keeping `--no-sources` as a belt-and-braces guard is defensible; the comment
needs to say that, not describe a table that was removed.

### 1.3 — S2 — The release image is built from a floating `uv:latest`

`Containerfile:9`

```dockerfile
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
```

`release.yml` builds the **published** `ghcr.io/behemotion/beherouter` image
from this file. A floating tag means two builds of the same git tag can use
different uv binaries, so the one artifact a downstream `helm install` pulls is
not reproducible from its own revision. Everything else in this repo is pinned
with a stated reason — `beheaxi @ ...@v0.1.2`, `fastmcp>=3.0.0`,
`plane-mcp-server==0.3.2` with `--exclude-newer`. This input is the exception.

### 1.4 — S2 — The image build does not use `--frozen`; CI does

`Containerfile:20` runs `uv sync --no-sources --no-dev`. `ci.yml` and
`release.yml` both run `uv sync --frozen --extra dev`, and the comment above it
explains that `--frozen` is load-bearing: it asserts the committed `uv.lock` is
self-sufficient.

The image build drops that assertion, so a `pyproject.toml`/`uv.lock`
divergence that fails CI would be silently re-resolved when the image is built.

**Verified not currently live** — image and lockfile agree today
(`fastmcp 3.4.5`, `mcp 1.29.0`, `httpx 0.28.1`, `uvicorn 0.51.0`,
`beheaxi 0.1.2` in both). The gap is latent.

### 1.5 — S2 — `.containerignore` with no `.dockerignore`

The repo ships `.containerignore` (excluding `.venv/`, `.git/`,
`.pytest_cache/`, `docs/superpowers/`, `registry.toml`, `data/`).

`podman build` reads it. **`docker/build-push-action` — used by both `ci.yml`
and `release.yml` — is BuildKit, and BuildKit reads `.dockerignore` only.** So
the local image and the published image are built from different contexts: the
published one copies `.git/` and anything else present into the build.

The practical cost on a CI runner is modest (a clean checkout has no `.venv`;
`docs/superpowers/plans/` and `docs/handoffs/` are gitignored, so they are
absent). But the intent of `.containerignore` is silently not honoured where it
matters most, and a locally-run `docker build` would behave differently again.

**Fix:** `ln -s .containerignore .dockerignore`, or make `.dockerignore` the
real file and symlink the other way.

### 1.6 — S3 — A `# noqa` for a rule that is not enabled

`src/beherouter/plugins/calendar/providers/google.py:167`

```python
_SEND_UPDATES = {"sendUpdates": "all"}  # noqa: RUF012
```

`RUF012` is not in the active rule set, so this suppression does nothing today.
It is evidence of the gap in §3.1: the author's editor lints with a wider
ruleset than CI does. The suppression becomes correct (and necessary) the
moment `RUF` is enabled.

## 2. Duplicate

### 2.1 — S2 — `probe`/`probe_args` is resolved in two places

`src/beherouter/gateway.py:41-45` and `src/beherouter/health.py:146-152` each
implement the same fallback: take the entry's pair if it has one, else the
plugin spec's.

This is notable because **the repo already fixed this exact problem once, for a
sibling field, and wrote down why.** From `plugins/__init__.py:130`
(`resolve_pinned`):

> ONE resolver, because `probe`/`probe_args` already taught this codebase what
> two call sites deciding the same thing separately costs — one gets enriched,
> they diverge, and the surface calls the right tool with the wrong arguments.

The lesson was learned, the cautionary tale was cited by name — and the pair it
is about is still resolved twice. The extraction target already exists next to
`resolve_pinned`.

Note the two sites are *not* identical: `gateway.load_backend` looks the plugin
up with `get()` (raises on unknown), `health.check_entry` with `PLUGINS.get()`
(tolerates it, so a bad registry still reports). `resolve_pinned` already solves
that shape by taking the plugin as a parameter — a `resolve_probe(entry, plugin)`
alongside it would follow the established pattern exactly.

### 2.2 — S2 — `API_KEY_MOUNT` is spelled twice

`plugins/plane_http.py:54` and `plugins/plane_http_apikey.py:51` both declare:

```python
API_KEY_MOUNT = "/http/api-key"
```

These two modules exist *specifically* to keep the two Plane HTTP mounts
straight — each one's `validate()` refuses the other's URL, and both docstrings
warn at length that confusing them attaches cleanly and then misbehaves. The
constant that encodes the distinction being written twice is the one place that
can silently drift.

`plane_http_apikey.py` already imports `PINNED`, `PROBE`, `PROBE_ARGS` from
`plane.py`, so importing the mount constant follows the pattern the file already
uses. (`plane_http.py` is the natural owner: it declares both mounts.)

Both `validate()` functions also end with the same `path.endswith("/mcp")`
check and near-identical message. Lower value to share — the messages
deliberately differ in what they recommend — but worth noting.

### 2.3 — S3 — Calendar providers duplicate their HTTP plumbing

`plugins/calendar/providers/google.py` and `.../microsoft.py` have
byte-equivalent `__init__` (`:31` / `:39`), `_request` (`:47` / `:61`) and
`_segment` (`:60` / `:74`) — ~25 lines, confirmed by an AST-normalised
structural scan (the only two structural duplicates in the whole of `src/`).

Everything that differs is already per-class: `BASE` is a module constant and
`_headers` is overridden (Microsoft adds the `Prefer: outlook.timezone="UTC"`
header). A small shared base in `providers/__init__.py` — which already hosts
the shared `raise_for_status` for exactly this reason — would carry `__init__`,
`_request` and `_segment` with `BASE` as a class attribute.

The `_segment` docstrings differ and both are valuable (they explain
*provider-specific* reasons the escaping matters). Those belong on the
subclasses or merged into the base's docstring; do not lose them.

### 2.4 — Not a defect: `gcal.build` / `m365.build`

`plugins/gcal.py:86-104` and `plugins/m365.py:78-97` are near-identical
(~18 lines each: a `provider` closure plus a `build_backend` call). Recorded
here so it is not rediscovered and "fixed".

Leave it. The divergence is meaningful — m365 has no `client_secret` (a
personal Microsoft account does not issue one, and declaring it would make a
working entry un-attachable per `registry.validate_entry`) — so a shared factory
would need to be parameterised by credential name, which is more machinery than
the eighteen lines it saves. The invariant that actually matters is already held
by a test: `test_gcal_and_m365_expose_identical_tool_schemas`.

## 3. Inefficient

Nothing here is a live performance problem — the gateway's scale is ~100 tools
per surface and a handful of concurrent callers, and the code says so. These are
recorded for completeness.

### 3.1 — S3 — `Catalogue.by_name` rebuilds a dict on every access

`catalogue.py:104-106`

```python
@property
def by_name(self) -> dict[str, ToolDescriptor]:
    return {d.name: d for d in self._descriptors}
```

`search_tools` binds it once (`surface.py:347`, correct). `describe_tool`
(`:366`) and `run_tool` (`:384`) call `catalogue.by_name.get(name)` — a full
O(n) dict construction per tool call, to do one lookup.

At 30 descriptors this is irrelevant. It is worth fixing only because the
invalidation point already exists and is free: `ensure_fresh` already sets
`self._index = None` on refresh, so caching `_by_name` beside it is one more
line in a place that is already correct.

### 3.2 — Not a defect: `ToolIndex.search`'s three passes

`search.py:67-92` runs up to three full corpus scans (exact / prefix / fuzzy),
each O(corpus × |query| × |tokens|). Bounded and documented: AGENTS.md fixes the
scale at ~100 tools per surface, and tiers 2 and 3 fire only when the previous
one under-fills `limit`. Leave it.

### 3.3 — S3 — Micro-issues a linter would auto-fix

From the broad ruleset, in `src/`:

- `RUF005` ×2 — `backends/cli.py:28,89`, list concatenation where unpacking is
  clearer and marginally faster.
- `PERF401` ×3 — manual append loops that are `list.extend`/comprehensions.

All auto-fixable. Not worth a hand edit; worth enabling the rule so they never
reappear.

## 5. Gate gaps — why each of the above survived

Every finding above got here because nothing mechanical was looking. Mapping
finding → missing gate is the input to the CI work.

### 5.1 ruff runs with only the **default** rule set

`pyproject.toml` configures `line-length = 100` and `target-version = "py312"`
but never selects rules, so ruff runs its default `E4, E7, E9, F` —
approximately pyflakes. Consequences:

- **`line-length = 100` is not enforced.** `E501` is not in the default
  selection. There is already a 106-char line (`tests/e2e/e2e.py:177`).
- No import sorting (`I`), no pyupgrade (`UP`), no bugbear (`B`), no
  **`ASYNC`** — in a codebase that is async end to end and whose one existing
  per-file ignore (`tests/e2e/*` → `ASYNC210, ASYNC221`) suppresses rules that
  are *not enabled anywhere*. That ignore has never done anything.

The good news: the full candidate ruleset finds only **25 issues repo-wide**,
5 auto-fixable. Turning it on is nearly free.

### 5.2 No type checker

No mypy, pyright or ty configuration anywhere. The code is thoroughly annotated,
so the cost of adopting one is mostly in the seams that are deliberately
untyped (`validate(config: dict)`, `policy_from_entry(entry, spec)`).

### 5.3 No coverage measurement

622 tests and no idea which lines they reach. Not necessarily a threshold gate —
but without a number, a PR that adds an unreached branch looks identical to one
that does not.

### 5.4 No dependency vulnerability scan

No `pip-audit`, no OSV, no Dependabot/Renovate config. The gateway holds
credentials for every backend it fronts.

### 5.5 Nothing lints the `Containerfile`

Findings §1.2–§1.5 are all in this one file, and no gate reads it. CI builds it
(good — it cannot rot silently) but never inspects it. `hadolint` catches the
floating `latest` tag (DL3007) and the missing `USER` (DL3002) directly.

### 5.6 No Python version is pinned anywhere

No `.python-version`, no `python-version:` input to `setup-uv`, no matrix.
`requires-python = ">=3.12"` lets the runner pick, while `target-version =
"py312"` asserts 3.12 to the linter. CI's actual interpreter is whatever
`ubuntu-latest` ships that month.

### 5.7 Actions are pinned to mutable tags

All nine `uses:` are major-version tags (`actions/checkout@v5`,
`softprops/action-gh-release@v2`, …). `release.yml` grants `contents: write` and
`packages: write`, so a compromised tag in that job can push to GHCR and cut a
release. SHA pinning is the standard mitigation.

### 5.8 `ci.yml` declares no `permissions:`

`release.yml` sets per-job permissions correctly. `ci.yml` sets none, inheriting
the repository/org default — which may be the legacy read-write token.

### 5.9 No `concurrency` group

Neither workflow declares one, so superseded pushes to a PR run to completion.
Three jobs including a container build and a QEMU-free image build.

### 5.10 The version-consistency gate runs too late and covers too little

`release.yml` checks tag == pyproject == chart appVersion **at tag time**. So
version drift is discovered when someone cuts a release, not on the PR that
introduced it — and `cli/app.py`'s version (§1.1) is not covered at all.

### 5.11 `tests/e2e/` never runs in CI

By design: it needs a live `plane-mcp-server` stack. Worth stating explicitly
somewhere, because "14/14 e2e" is quoted in `AGENTS.md` as a current fact while
nothing re-establishes it.
